# Sunny — Power Architecture (Current)

**Living document — always reflects the current active development state.** For the frozen snapshot captured at the Sunny V1 baseline (2026-08-07), see the matching file in `docs/V1/`. Update this file, not `docs/V1/`, when things change.

## Current rail layout (verified, corrected 2026-08-01)

```
Shared 5V rail:  WS2812B LEDs, MAX98357A amplifier, DRV8833 motor driver
3.3V rail:       INMP441 microphone only
Common ground:   across ESP32-S3 and all peripherals
```

**History note**: an earlier version of this project's documentation
(`AGENTS.md`, `README.md`, `docs/DRV8833_MOTOR_BRINGUP.md`) incorrectly
stated that the DRV8833 (and, separately, the MAX98357A) ran from the
ESP32's own 3.3V pin. This was corrected on 2026-08-01 after
investigation confirmed both actually run from the shared 5V rail. The
correction is reflected in `AGENTS.md`, `README.md`, and this file.
Historical documents that predate the correction (see
`archive/motor_bringup/` and `archive/speaker_bringup/`) were **not**
rewritten — they're preserved as an accurate record of what was
believed at the time, with a pointer added to the correct current
value.

ESP32 GPIO logic signals (I2S, buttons, LED data) remain 3.3V
regardless of which rail a peripheral's own power comes from.

## The real electrical risk

> The shared 5V supply, distribution wiring, connectors, and grounding
> must support the combined peak load and noise generated by the LEDs,
> amplifier, and motor simultaneously.

This is **not yet physically measured or validated** as of the V1
baseline. Three simultaneous 5V loads (LEDs, amplifier, motor) share
one supply, with no dedicated per-peripheral regulation.

## What has been physically observed

- **Motor engagement measurably disturbs LED output** while the two
  share this 5V supply (correlated with shared-supply power
  contention; no exact voltage sag has been instrumented). Motor
  movement is reliable with LEDs muted, inconsistent/weak while LEDs
  are actively rendering.
- Power decoupling (1000 µF + 1 µF, both shunt across 5V/GND — see
  `ELECTRICAL.md`) was added specifically to address amplifier noise;
  it has not eliminated the residual speaker buzz/static (see
  `SPEAKER.md`).
- No ESP32 resets, brownouts, or watchdog failures were observed during
  the final successful motor bring-up validation (forward/reverse/stop
  via live serial commands).

## LED-side software power limiting

`main.cpp`'s `applyPowerLimit()` estimates per-frame LED current as
`NUM_LEDS * LED_IDLE_MA_PER_LED + (sum of all R+G+B values) *
LED_MAX_MA_PER_CHANNEL / 255` and scales the whole frame down
proportionally if it exceeds `LED_CURRENT_LIMIT_MA` (`Config.h`,
default 1000mA), printing a throttled `[POWER]` warning at most once
every 2 seconds when it does. **This is a software estimate for
bring-up safety, not a substitute for correct electrical power
design** — it cannot protect against a supply undersized for the LEDs'
physical maximum draw.

## Mitigations that exist today (workarounds, not fixes)

- **`MotorPowerGuard`** — mutes LEDs immediately before the motor
  engages and restores them shortly after it stops, so LED and motor
  current draw don't overlap during `IDLE_SWAY`/`ExpressiveMotion`/the
  motor+LED diagnostics. Explicitly documented as a **temporary
  bench-development workaround**, not a production fix — the real fix
  is a dedicated external motor supply.
- **`DanceEngine`/`MusicMotorController` deliberately do NOT use
  `MotorPowerGuard`** — by explicit prior design decision, so LEDs stay
  exactly as the user set them through a dance/music session. This
  means sustained high-duty PWM movement and full LED rendering can
  draw from the shared 5V rail simultaneously for as long as a session
  lasts. **Whether this causes visible disturbance, brownout, or
  resets during real extended use has not been physically confirmed.**

## No current-sensing or thermal-monitoring hardware

Over-current, stall, and thermal conditions cannot be detected in
software anywhere in this project — only avoided via conservative
timing/duty choices (see `MOTOR.md`'s M80 floor and the 2000ms
max-energized safety net).

## Recommended next step

Not yet done: a dedicated external motor power supply, common-grounded
with the ESP32, sized for actual combined draw including motor startup
inrush — see `ROADMAP.md` (listed under V1.1) and `ELECTRICAL.md`'s
"Future production recommendations."
